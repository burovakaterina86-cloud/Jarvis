# ADR 0013 — Независимая проверка результата запускает мост

- Статус: принято (2026-10-05). Уточняет ADR 0001 («Python — тонкий мост»).
- Контекст: аудит 2026-10-05 показал, что роль `reviewer` есть, но ни один навык её не вызывает, а решение «готово» принимает сам исполнитель. Субагент-проверяющий внутри той же сессии получает задание от исполнителя — тот сам решает, что ему показать. Нужна проверка со свежим контекстом и по заранее согласованным критериям (план P2.1).
- Решение: после существенного хода чата (был план, появился комплект в `essa-ai/content/`, изменился код) `task_router` запускает отдельный процесс `claude -p` через тот же мост: без `--resume` и с `--no-session-persistence` (история исполнителя недоступна), с `runtime/reviewer-settings.json` (разрешены только `Read`, `Glob`, `Grep`, `StructuredOutput`; Guard в режиме бота), промптом `runtime/prompts/review.md` и `--json-schema` вердикта `pass | fix | fail`. На вход — только сообщение владелицы, план, список изменённых файлов, итоговый ответ исполнителя и хвост `pytest`, если менялся `.py`. `fix` → замечания уходят исполнителю в его сессию → повторная проверка; не больше двух кругов. Итог владелице — ответ исполнителя и строка вердикта. Всё в журнале: `review_verdict`, `task_done.review_verdict/review_rounds`. Выключатель — `JARVIS_REVIEW=off`. Это не «умный» Python в смысле ADR 0001: мост не выбирает навыки и не толкует намерение, он детерминированно запускает ещё один ход по фиксированному правилу.
- Проверено живьём: P2.0 (`tests/smoke_cli_capabilities.py`) и прогон настоящего ревьюера на нарочно плохом посте — вердикт `fail` с точным списком. Живой прогон нашёл, что `--json-schema` сдаёт ответ инструментом `StructuredOutput`, которого не было в `policy.yaml`, — добавлен в `read_tools`.
- Альтернативы: (а) субагент `reviewer` внутри хода исполнителя — отвергнуто: не независим, контекст задаёт исполнитель; (б) проверка только по просьбе владелицы — отвергнуто: она не ревьюер кода и текстов на каждом шаге; (в) без ограничения кругов — отвергнуто: расход лимита и риск бесконечного «исправь».
- Последствия: на существенных задачах расход лимита примерно вдвое больше (каждый запуск проверяющего и исправления тратит дневной лимит запусков); ответ приходит позже. Проверяющий может ошибаться — его вердикт показывается владелице, а не скрывается. Простые ответы, планы и задачи по расписанию не проверяются.
